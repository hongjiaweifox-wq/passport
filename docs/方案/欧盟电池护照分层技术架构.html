欧盟电池护照
分层技术架构方案

基于需求梳理，定义平台能力分层和核心数据流，并链接各层开发级技术方案。本稿聚焦“数据从哪里来、如何结构化、如何形成护照并安全提供访问”。

方案阶段：分层技术设计产品对象：阳台光伏一体机 / 户用储能中的电池版本：Draft 0.2

01 · 架构目标

建设一套可汇聚多来源电池数据、形成规范化护照档案，并通过稳定标识和分级授权对外提供信息的平台能力。

统一汇聚

接收企业填报、文件导入、现有业务系统和设备运行侧数据。

规范治理

将来源各异的数据转换为统一、可校验、可追溯的电池护照结构。

可信发布

经过校验与责任主体审核后发布护照，并支持持续更新和历史追溯。

安全访问

通过电池唯一标识和二维码提供入口，按公开或授权范围展示数据。

核心设计原则：护照属于电池对象；电池 SN 可作为标识候选，但需要确保唯一、稳定并能映射至护照。护照建档和发布不依赖终端设备先激活连云。

02 · 总体分层架构

建议先按六层理解。数据自下而上汇入和治理，应用访问自上而下经过统一入口与权限控制。

数据映射、标准化、完整性校验、规则判定、质量状态、审核工作流、字段访问分类。将“收集到的数据”转成“可用于护照发布的数据”，记录来源、责任人和审核状态。查看 L4 技术方案 →

L3 · 结构化数据层

统一的电池护照数据模型与主数据档案。按电池型号、批次、单体电池、设备关联、生命周期事件组织，保留字段版本与数据血缘。查看 L3 技术方案 →

L2 · 数据接入与导入层

数据采集入口：模板/文件导入、人工填报、业务系统接口、设备云/BMS 接入。负责接收、初步解析、格式识别、导入任务状态和失败反馈，不在此层直接对外发布。查看 L2 技术方案 →

↑
L1 · 数据源层

数据生产方与现有数据所在系统。电池制造商/供应链、品牌与产品管理系统、测试/合规资料、涂鸦设备云和后续服务/回收伙伴。查看 L1 技术方案 →

横向支撑能力（贯穿各层）：组织与身份、角色权限、审计日志、隐私与安全、配置和规则版本、运维监控、数据备份与迁移。它们不是单独的数据流步骤，而是各层共同遵循的基础能力。

L1 · 数据源与接入规范

数据责任、数据来源清单、CSV/JSON 模板、标识及数据质量约定。

L2 · 数据接入与导入层

文件/API 导入、异步任务、解析、幂等、行级错误和安全扫描。

L3 · 结构化数据层

电池型号、修订、批次、单体、设备关系及生命周期数据模型。

L4 · 数据治理与合规层

字段字典、适用性规则、质量校验、审核及发布门禁。

L5 · 护照服务层

护照标识与版本、发布状态机、二维码解析、公开投影和受控访问。

L6 · 应用与访问层

管理工作台、扫码 H5、OIDC 登录、权限映射、国际化与测试。

共同约定：基础包 com.tuya.passport；REST /api/v1；schema dpp-schema/1.0；数据以 org_id 隔离；平台主键、外部标识与 QR public_code 分离。各详细方案明确本层边界和接口契约。

03 · 数据源与接入方式

来源类别数据示例首期建议接入方式架构定位
制造商 / 供应链电池型号、化学体系、额定参数、生产信息、组成及相关证明材料管理工作台填报 + 标准模板批量导入首期主要基础数据源
品牌 / 产品业务系统产品 SKU、型号关系、投放市场信息、经济运营者信息模板导入；后续通过 API 同步补充产品与市场主数据
测试与合规资料性能耐久、碳足迹、回收含量、声明和证据文件附件上传并关联字段/型号；后续系统集成数据依据与审核输入
涂鸦 IoT / 设备云 / BMS设备关联、运行状态及适用的单体电池动态数据首期可先不阻塞；后续经授权 API 接入运行及生命周期数据源
服务与生态伙伴维修、更换、再利用、再制造、回收等事件后续通过伙伴工作台/API 逐步接入生命周期补充数据源

建议初期优先用结构化模板和人工审核跑通闭环，验证字段定义及责任链后再增加系统接口；设备云接入属于数据来源之一，而不是生成护照的前置条件。

04 · 端到端核心数据流

1 · 来源提供供应链、业务系统、文件资料或授权设备数据进入平台。
2 · 接入解析文件/接口识别，检查基本格式，生成导入结果和问题反馈。
3 · 结构化归档映射到统一电池数据模型，关联型号、批次、单体与来源证据。
4 · 治理审核执行规则检查、补齐缺项、责任人确认和发布审批。
5 · 护照服务绑定电池唯一标识，形成版本化护照并通过二维码/接口提供访问。
数据状态建议：已接收 → 已解析 → 待补充/待校验 → 待审核 → 已发布 → 已更新/已失效。只有完成治理和授权审核的数据进入公开或受控的护照展示。

05 · 统一结构化数据的概念模型

逻辑上先确定数据对象，不在本阶段定义物理数据库或字段级接口。

电池型号

描述型号级属性及相对稳定的技术、性能和合规信息。

生产批次

承接批次相关的生产、测试或材料差异信息。

单体电池

以电池 SN 或平台标识定位实体电池，关联型号/批次与二维码入口。

设备关联

连接电池与阳台光伏一体机、户用储能系统等设备；支持更换和关系历史。

生命周期事件

承接运行数据、维修、更换、再利用、再制造、回收等动态信息。

来源与证据

记录字段来源、责任方、导入批次、证明材料、校验及审核情况。

具体字段目录、单位/枚举、法规条款映射、可见级别和必填规则，作为下一阶段的数据字典专题再细化。

06 · 核心模块边界

模块主要职责本阶段关注
数据接入中心管理填报、文件批量导入、外部接口与后续 IoT 接入。明确入口类型与来源责任，不展开具体 API。
数据模型与档案中心维护统一电池对象、型号/批次/单体关系及数据版本。先确认逻辑对象和关系。
数据治理中心标准化、校验、质量状态、证据管理与审核流程。明确“接入数据”和“可发布数据”的边界。
护照管理中心创建护照、绑定标识、版本维护、发布与失效处理。明确护照对象与电池标识关系。
护照访问服务二维码解析、公开页面、授权查询与数据导出。明确统一访问入口和分级访问原则。
平台横向支撑组织权限、安全、审计、规则配置、监控和备份。作为所有模块的共性能力纳入设计。

07 · 方案状态与后续

本稿定位

本页维护六层逻辑架构、数据流和方案索引；各层开发级设计、接口示例、数据模型与验收点请从上方索引进入对应方案。

仍需项目化确认

法规字段/访问权限、试点 SKU 与电池边界、各品牌责任主体、平台组织标准、正式 SLA 与容量目标。

建议实施顺序

  1. 由产品/合规确认试点 SKU、电池组成、SN 命名规则及投放欧盟市场的责任主体。
  2. 由合规 owner 审核法规字段字典与公开/受控字段映射，作为 L4/L5 开发的基线。
  3. 按 L1→L2→L3→L4→L5→L6 完成模块联调；可并行开展 L1 数据盘点与 L6 原型。
  4. 选定一款阳台光伏一体机或户储产品跑通从源数据到二维码访问的端到端试点。
各层文档提供开发基线，不取代业务、法规、安全团队确认。法规要求、实际责任边界和组织技术规范优先于方案草案。

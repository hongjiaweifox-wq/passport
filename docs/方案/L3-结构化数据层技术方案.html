L3 · CANONICAL DATA MODEL

结构化数据层技术方案

将导入候选数据持久化为有租户边界、可追溯、可版本管理的电池主数据和生命周期记录，提供给治理/护照层使用。

Draft 0.1Java 17 · MySQL 8schema dpp-schema/1.0

1. 职责和数据边界

L3 是平台规范化业务数据的权威存储层，管理电池型号、修订、批次、单体、设备绑定、生命周期事件和证据引用。L1 定义字段语义；L2 交付 canonical 候选数据；L4 拥有字段字典、法规规则和审核结论；L5 读取已审核快照构建护照。

不做：不自行推导法规合规结论、不定义公开字段分类、不直接构建护照 JSON、不将 Tuya device_id 作为电池身份、不物理删除已引用/已发布记录。

工程模块：passport-domain（模块化单体），包 com.tuya.passport.data；DB schema 同库按模块拥有表，Flyway migration 按模块前缀编号；统一使用 MySQL 8、MyBatis-Plus、UUID CHAR(36)。

2. 领域对象与关系

对象主粒度核心关系/规则
BatteryModel制造商命名空间下的产品型号一个型号包含多个 Revision；型号基础资料不可覆盖历史修订。
ModelRevision某版本的技术/合规声明保存结构化属性 JSON、schemaVersion、状态、来源和生效区间。
ProductionBatch批次归属 ModelRevision，可关联证据及批次属性。
BatteryUnit可识别的电池实体由 issuer_code + normalized_sn 唯一；原始 SN 永久保留，不能复用。
DeviceBinding电池与设备/系统关联时段历史保留；同一电池同时最多一个 active binding（按业务定义设备层级）。
LifecycleEvent某单体电池事件追加写入；更正采用 supersedes_event_id，不原位修改。
EvidenceAssetRef证据文件引用与元数据文件实体由共享 OSS 能力管理，本表仅引用 asset_id/checksum/MIME/保留标签。

一期核心属性采用固定列 + JSON 扩展列，避免尚未证明查询需求前建立通用 EAV。扩展字段须经 L4 字段字典登记，不允许任意键进入发布数据。

3. 核心 DDL（MySQL 8）

CREATE TABLE bp_battery_model (
 id CHAR(36) PRIMARY KEY, org_id CHAR(36) NOT NULL,
 issuer_code VARCHAR(64) NOT NULL, model_code VARCHAR(64) NOT NULL,
 manufacturer_name VARCHAR(200) NOT NULL, battery_category VARCHAR(24) NOT NULL,
 created_at DATETIME(3) NOT NULL, updated_at DATETIME(3) NOT NULL,
 version BIGINT NOT NULL DEFAULT 0, deleted_at DATETIME(3) NULL,
 UNIQUE KEY uk_org_issuer_model (org_id,issuer_code,model_code),
 KEY idx_org_category (org_id,battery_category)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE bp_model_revision (
 id CHAR(36) PRIMARY KEY, org_id CHAR(36) NOT NULL,
 model_id CHAR(36) NOT NULL, revision_code VARCHAR(64) NOT NULL,
 schema_version VARCHAR(32) NOT NULL, rated_capacity_kwh DECIMAL(12,4),
 rated_voltage_v DECIMAL(12,4), chemistry_code VARCHAR(40),
 attribute_json JSON NOT NULL, source_ref VARCHAR(128) NOT NULL,
 effective_from DATE NOT NULL, effective_to DATE NULL,
 status VARCHAR(20) NOT NULL, created_at DATETIME(3) NOT NULL,
 UNIQUE KEY uk_org_model_revision (org_id,model_id,revision_code),
 KEY idx_org_status (org_id,status),
 CONSTRAINT fk_revision_model FOREIGN KEY(model_id) REFERENCES bp_battery_model(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE bp_battery_unit (
 id CHAR(36) PRIMARY KEY, org_id CHAR(36) NOT NULL,
 issuer_code VARCHAR(64) NOT NULL, sn_raw VARCHAR(128) NOT NULL,
 sn_normalized VARCHAR(128) NOT NULL, model_revision_id CHAR(36) NOT NULL,
 batch_id CHAR(36) NULL, manufactured_at DATETIME(3) NULL,
 source_system VARCHAR(64) NOT NULL, source_record_id VARCHAR(128) NOT NULL,
 status VARCHAR(20) NOT NULL, created_at DATETIME(3) NOT NULL,
 version BIGINT NOT NULL DEFAULT 0,
 UNIQUE KEY uk_org_issuer_sn (org_id,issuer_code,sn_normalized),
 UNIQUE KEY uk_source_record (org_id,source_system,source_record_id),
 KEY idx_org_revision (org_id,model_revision_id),
 CONSTRAINT fk_unit_revision FOREIGN KEY(model_revision_id) REFERENCES bp_model_revision(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE bp_device_binding (
 id CHAR(36) PRIMARY KEY, org_id CHAR(36) NOT NULL,
 battery_unit_id CHAR(36) NOT NULL, device_id VARCHAR(128) NOT NULL,
 bound_at DATETIME(3) NOT NULL, unbound_at DATETIME(3) NULL,
 change_reason VARCHAR(255), created_at DATETIME(3) NOT NULL,
 KEY idx_org_unit_active (org_id,battery_unit_id,unbound_at),
 KEY idx_org_device (org_id,device_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

同样模式补齐 batch、lifecycle_event、evidence_ref、outbox。所有业务表均带 org_id；唯一索引均纳入 org_id。外键不能单独替代跨租户校验；repository 查询必须显式 org_id。Flyway migration 定义真实 DDL，不允许生产依赖自动建表。

4. 写入 API / 事件

接口用途权限
POST /api/v1/models创建电池型号与初始修订data:write
POST /api/v1/models/{id}/revisions新增不可覆盖的型号修订data:write
POST /api/v1/battery-units:batchUpsert按 source record 幂等登记单体data:write
GET /api/v1/battery-units/{id}租户内查询单体及当前关系data:read
POST /api/v1/battery-units/{id}/bindings创建绑定/更换关系data:write
POST /api/v1/battery-units/{id}/events追加生命周期事件lifecycle:write

写入使用 Idempotency-Key，响应返回记录 ID 和 traceId。冲突：同 SN 不同 model/source payload 返回 DATA_IDENTITY_CONFLICT；不得自动合并或覆盖。L3 事件：bp.data.model-revision.v1、bp.data.unit-registered.v1、bp.data.lifecycle-event.v1。Envelope 与 L2 一致。

5. 事务、版本与并发

  • 采用乐观锁 version；更新请求带 expectedVersion，不匹配返回 409 DATA_VERSION_CONFLICT。
  • 型号修订、单体注册与 outbox event 在同一 MySQL 事务提交；MQ publisher 独立读取 outbox，成功后标记 published。
  • SN 规范化：trim + Unicode NFC；大小写规则按 issuer 配置；保留 sn_raw，禁止删除前导零/内部符号。唯一键由 org + issuer + normalized SN 构成。
  • 更换绑定采用事务：结束旧 active binding，再新增一条；失败回滚。并发请求锁定 unit 行或通过唯一活跃约束策略保证仅一条。
  • 单体、已发布修订及事件禁止硬删除；撤销用状态/软删除并产生审计。删除请求需评估法律保留义务。

6. 安全、租户和数据保留

  • JWT org_id 必须从认证上下文提取；服务层函数显式传入 orgId，Mapper 强制 org_id 条件。
  • 跨租户对象查询统一返回 404；新增/绑定时验证所有关联对象属于同 org。
  • MyBatis-Plus TenantLineInnerInterceptor 作为防漏项；对原生 SQL、批量 SQL 与后台任务增加负向测试。
  • restricted/internal 属性与证据 metadata 不得由 L3 直接公开；由 L4 字典及 L5 投影控制。
  • 审计字段：actor、org、source system、traceId、before/after hash、reason、occurredAt；操作审计写共享 append-only sink。
  • 备份/恢复及归档策略按法律留存、业务 SLA 另行批准；个人数据尽量不进入电池主档。

7. 测试、验收与开发任务

  1. 同 org 下唯一 SN 生效；不同 org 可有同 SN；同 issuer 大小写规则符合配置。
  2. 跨租户读写、关联对象越权、原生 SQL 绕过租户拦截的负向测试均通过。
  3. 同 source record 重试幂等；同 SN 异 payload 冲突；并发绑定不会产生两个 active 关系。
  4. revision 与 lifecycle event 只追加版本；乐观锁冲突返回 409；数据库恢复后 outbox 可补发。
  5. 执行 Flyway 空库迁移及上一版本升级；索引查询计划覆盖 org_id + SN/model。

任务：定义领域 DTO/映射 → 建 Flyway 表和 Mapper → 实现型号/修订 → 单体/SN 幂等 → 绑定与事件 → outbox/MQ → 权限和审计 → 集成与迁移测试。

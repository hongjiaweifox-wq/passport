L6 应用与访问层读取 L5 的公开/受控视图；不在本 ER 范围内重复建表。跨层通常以稳定 ID、组织键和快照/业务键关联，由服务层执行租户校验。

一、当前可运行原型 ER（L1–L5，已实现）

当前原型是单体 Spring Boot + H2；原有 6 张 L1/L2 表之外，现已新增 L3/L4/L5 的 JPA 原型实体表。L1 集合表关系由 ORM 映射；各层多数业务关联由服务层按 org 与业务键校验。下方原 ER 示意图保留展示 L1/L2 关系；新增层表与差异见本节后续表字典。

重要：原型的 l2_import_job.source_code 不持有 l1_data_source.id 外键；上传时通过进程内 L1 查询确认来源启用且获准该模板，任务保存来源代码/名称快照。删除/改名来源不会通过数据库级约束自动级联历史任务。

跨层关系矩阵

父 → 子基数连接键约束方式一致性/校验责任
L1 data source → L2 import job1 : N（逻辑）原型 org_code + source_code无物理 FK；任务保存 source name snapshot上传时校验来源启用、模板授权；历史快照可审计
L2 import job → staging rows1 : Norg + job_id + attempt_no原型无 FK；目标 staging DDL 待补每次重试递增 attempt，保留历史行与错误
L2 import job → row errors1 : Norg + job_id + attempt_no原型无 FK；目标 DDL 有 job_id，但需补 attempt_no错误报告按 job/attempt 分页与导出，原始值仅存 hash
L2 canonical → L3 battery unit / revision1 : 0..Norg + source_system + source_record_id + entity_type跨层业务幂等键，无跨服务 FK消费者幂等、schema 映射、冲突显式处理
L3 model → revision1 : Nbp_model_revision.model_id目标 DDL 有 FK同 org 校验；修订只追加
L3 revision → battery unit1 : Nbp_battery_unit.model_revision_id目标 DDL 有 FK同 org 校验；SN 按 org + issuer + normalized 值唯一
L3 unit → device binding1 : N（历史绑定）battery_unit_idDDL 未列 FK，逻辑关系事务结束旧绑定、插入新绑定；保证最多一个 active
L3 object → L4 validation / review1 : Nsubject_type + subject_id + org_id多态逻辑引用通过 subject_type 分派至 L3 主体，并校验租户
L4 reviewed snapshot → L5 passport1 : N 版本候选battery_unit_id + snapshot_hash跨层逻辑关系，无 FK仅审核通过快照可发布，hash 可回放验证

关系建模建议：同一模块内生命周期明确、数据同库且归属稳定的聚合关系可定义外键；跨层边界（L2→L3、L3→L4、L4→L5）保留业务键/快照引用，不通过跨模块 FK 耦合。任何 FK 均不能替代多租户下的同组织校验。

方案差异与待确认项

目标 DDL 与幂等描述不一致

bp_import_job 写了 UNIQUE(org_id,id)，但正文要求对每组织 Idempotency-Key 幂等；建议 DDL 增加 idempotency_key 并以 (org_id,idempotency_key) 唯一。

导入重试历史缺少列

目标 bp_import_row_error 未含 attempt_no，无法自然区分每次重试的错误集；唯一键也需纳入 attempt。

来源幂等键缺少实体类型

bp_battery_unit.uk_source_record 是 (org_id,source_system,source_record_id)；L1 契约还包含 entity_type，需确认是否扩展唯一键。

跨租户 FK 策略需要统一

model/revision/unit 的 FK 未将 org_id 纳入复合键；应用服务须确保父子租户一致。device binding 与 passport/version 目前未声明 FK，应明确保持逻辑引用或补齐复合 FK。

实现边界：当前原型只有 L1/L2 H2 表；L3/L4/L5 及目标 MySQL DDL 仅为分层方案。生产迁移建议由 Flyway 管理版本化 DDL，禁用生产环境 Hibernate 自动建表。本文不把待补表画成已存在的正式结构。

待补充实体：L2 staging record；L3 batch、lifecycle_event、evidence_ref；L2/L3/L4/L5 共享 outbox（具体模块归属待定）。L4 的 rule set/version、validation_issue、review_action、applicability_result、audit 也尚无完整 DDL。
